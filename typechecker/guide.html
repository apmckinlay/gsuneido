Suneido Typechecker Guide

This guide explains what the Suneido static typechecker reports, why it reports it, and what to change. It is written for two readers: a developer who sees an error or warning in the IDE and wants to know what it means, and a developer who wants to understand how the checker arrives at its answers and why it is sometimes wrong. Everything here describes the checker as it behaves today; where the checker is known to be wrong or limited, the guide says so and gives a workaround.

What the checker is and how to run it

What it checks and what it produces

The typechecker is a static analysis of Suneido source. It checks one class (or one function) at a time, together with that class's base classes and a set of references: other classes and functions that the class calls, supplied so their return types can be resolved. It does not run any code. It reads the source, infers a type for every parameter, local variable, member and method return, and then checks the code against those types and against a table of builtin signatures.

For each class it produces two things:

  • Types. For every method, a type for each parameter and local and a $return type; for the class, a type for each member written as a literal in the class body. Types are printed as strings such as number, false|string or ?|object (see Reading a type).
  • Diagnostics. A list of Errors and a list of Warnings, each with the class, method, position (line and column), a message, and, for some, a configuration flag.

The checker never changes its inferred types because of a check failure. If it decides x = "a" + 1 is wrong it still types x as number, because + always yields a number, and reports the operand separately. Inference and checking are independent.

Calling it from Suneido

The builtin class TypeChecker has four methods:

CallReturns
TypeChecker.Infer(arguments, references = #(), config = #())a result object with types and diagnostics

arguments and references are lists. Each element is either a source string (the class is then named Class0, Class1, ... by position) or an object #(src: "class { ... }", name: "Foo"). The name matters: it is how references are found when the checked code says new Foo() or Foo.Bar(), and it is the class reported on every diagnostic. Named members of the outer list are ignored. Passing something that is not an object throws can't convert String to Object; an element that is neither a string nor an object with src throws TypeChecker.Infer: arguments[i]: must be a string or an object with src.

The result object looks like this:

#(method: "TypeInfer",                 // or "TypeAnnotate"
  result: (                            // one entry per argument, in order
      #(methods: #(Foo: #(x: "number", s: "string", $return: "false|string"),
                   New: #()),
        members: #(items: "false|object", count: "number")),
      ...),
  diagnostics: #(
      errors:   ( #(class: "Foo", method: "Bar", pos: 122, line: 7, col: 3,
                    msg: "[0.90] operator \"+\" expects number, got string"), ... ),
      warnings: ( #(class: "Foo", method: "Bar", pos: 40, line: 3, col: 9,
                    msg: "[0.20] operator \"$\" expects string, got number",
                    flag: "strictStringConcat"), ... )),
  version: Built)

A few details of the result: $return is absent when the return type could not be determined; parameters, locals and members whose type is unknown are omitted; members lists only members that are written as literals in the class body (a member that exists only because New assigns it never appears); a local's type is the union of every type it had anywhere in the method; line and col are 1-based and col counts bytes, so a tab is one column; a diagnostic with no position lands at line 1, column 1; flag is present only on the two configurable families. A function passed as an argument appears as a single method named after the argument.

The IDE path. The IDE does not call TypeChecker.Infer directly. TypeCheckHelper.Run(name, TypeCheckerMethods.Infer) (and TypeCheckHelper.Check) build the class's lineage base-first (TypeCheckHelper.OrderedSrc, via TypeCheckerLineage), collect references from every new X, X(...) and X.Foo(...) name in the source (each reference chain also base-first), and hand both to TypeCheckerBuiltin.Check. That in turn loads the Suneido-side signature layer once per process (TypeCheckerSignatures(), which calls RegisterSignatures with the stdlib table) and calls TypeChecker.Infer(orderedSrc, refs, TypeCheckerPolicy()). The policy is:

TypeCheckerPolicy()  =>  #(strictCrossTypeCompares: #warn,
                            strictStringConcat: #off,
                            confidence: ">=0.70")

The consequence of that policy is discussed in the next section: in the IDE you only ever see diagnostics scoring 0.70 or higher, which is every ordinary error and exactly one kind of warning. To see everything, run TypeChecker.Infer yourself with config: #(confidence: 'all').

The confidence prefix and the confidence filter

Every message starts with a bracketed confidence between 0 and 1, for example [0.90] method "Size" on `x` not applicable to receiver of type string. The prefix is part of the message string; anything that matches message text must strip it. The examples in this guide omit it unless the value matters.

The score is not a measure of evidence; it is a fixed ladder decided by which kind of diagnostic this is:

ScoreWhich diagnostics
1.00the internal-error diagnostic only
0.90every ordinary error: return contracts, receiver mismatches, argument types, argument counts, member access, static members, Assert conflicts, boolean contexts, and operator errors whose operand is a single type
0.75the "is passed on to ... which requires" error (an inferred requirement)
0.70the "passed both positionally and by name" warning; operator errors whose operand is a clean union such as number|string
0.40operator errors whose operand is a dirty type such as ?|number
0.35every ordinary warning: guesses, "cannot prove" argument and return warnings, annotation typos, discarded named arguments
0.25the operator "cannot prove" warning and the dirty-union receiver warning
0.20anything carrying a configuration flag (strictStringConcat, strictCrossTypeCompares), even when the configuration has promoted it to an error

Two things follow. First, 0.90 on a return, callsite, arity or boolean error means "an unflagged error", not "certain": only operator checks look at the shape of the operand when scoring, so return type false|number|object not assignable to declared number is 0.90 while the same union under + is 0.70. Second, under the IDE policy >=0.70 the flagged families are invisible whatever their configured level, and so are the 0.40 operator errors on dirty types and all 0.35 and 0.25 warnings.

The confidence configuration value accepts all (or blank, or absent) for no filter, or an operator and a number: >=0.70, <=0.5, ==0.9, =0.9, >0.5, <0.5. A bare number means >=. Anything else fails the whole call with config.confidence: invalid threshold "high" (want e.g. ">=0.70"). Diagnostics are sorted by confidence descending; within one confidence they are in argument order, then by method name, then statement order. They are not in line order.

A misspelt key is silently ignored and the default applies, so strictStringConcats: #off changes nothing and raises no error.

Base classes must be arguments, base-first

The checker keeps one shared environment for all the arguments in a call. Each argument is checked in order, and everything it publishes (member types, method return types, guessed-value taint, Assert facts) stays in the environment for the arguments that follow. This is how inheritance works: when you check Derived, you pass #(Base, Derived) as arguments, in that order, and Derived's calls to .M() and super.M() resolve through what Base published.

Three rules follow, and all of them fail silently when broken:

  • The lineage must be in arguments, base-first. Reversing the order loses inheritance. Putting the base in references instead of arguments also loses it: both .M() and super.M() come back unknown.
  • Unrelated classes in one call contaminate each other. With arguments #(A, B) where A = class { x: "s" } and B = class { Bar() { return .x } }, B.Bar is reported as returning string, although B alone has no x. Check one class (with its lineage) per call; TypeCheckHelper.OrderedSrc does exactly that.
  • References are pre-digested once and are never re-run. A reference sees the references before it (so reference chains must also be base-first), but a reference never sees the arguments, and a class that appears in both lists is resolved through the reference version when other code calls it.

Reading a type

The primitive types

Instances, unions and ?

Instances. A capitalised name such as Foo or Control means "an instance of exactly that class". Instances are compared by name only: an instance of a subclass does not fit Control, and Foo does not fit object. Instances come from new Foo(), from calling a class that has no CallClass, and from annotations. Calling a method on an instance whose class is not in the references is silently unknown.

Unions. a|b means "either". Arms are printed sorted alphabetically, so false|string and Alpha|Zed|number|string (capitalised instances sort before lowercase primitives). Two or more of true, false, boolean collapse to boolean, so a false sentinel that is ever assigned true stops being a sentinel. Foo|object stays as written; nothing is absorbed.

? means "or something the checker could not determine". A type containing ? is called dirty. It is printed first, not last, because ? sorts before every letter: ?|false, ?|number|string, ?|object. A dirty type says "I saw these arms, and there may be others". When there are no known arms at all the type is simply unknown; ? never appears alone.

Dirt matters for what the checker says. On a dirty value most checks downgrade to a "cannot prove" warning at 0.25 or 0.35 instead of an error, and the IDE policy hides those. There are three exceptions you will notice: a boolean context (if x) ignores dirt and reports a full 0.90 error if any known arm is not boolean; a member or subscript access on a dirty receiver is not checked at all; and an argument whose type is pure unknown is silently accepted while a dirty union argument gets a warning.

The false sentinel idiom

Many builtins are declared as returning false|something: Query1 and QueryFirst return false|object, .Find returns false|number, and .GetDefault(k, false) follows its default. A member written as items: false and a parameter written as x = false carry the same idea. The checker takes the false arm literally: rec.name on a false|object is an error (member "name" on `rec` not readable on at least one path of union receiver false|object; no members on false), and n + 1 on false|number is an error. The large majority of errors in real code are this shape: a false|X value used as if it could not be false. The whole of Narrowing is about how to tell the checker that it cannot be false here.

Writing an annotation

Parameters and returns take annotations in the source:

Foo(x :string|false, count :number = 0) :object
    {
    ...
    }

The rules:

  • The text after : is split on |. Each arm is a builtin type name or a class name.
  • Builtin names are case-insensitive: string, String and STRING all mean string; record and Record mean object.
  • A name that starts with a capital letter and is not a builtin name means an instance of exactly that class: :Control accepts a Control and rejects every subclass. ? and ! are allowed in the name, so :Foo? is legal.
  • A parameter's default must fit its annotation. x :string = false is an error (param "x" default has type false, annotation says string); write x :string|false = false.
  • A dot-parameter can be annotated too: New(.flag :boolean = false).

Typos are only warnings, and that is the trap. x :strin produces a 0.35 warning (hidden by the IDE policy) and the parameter is then treated as unannotated, so the guesses you were trying to remove persist and nothing says why. x :string|strin produces the same warning and a dirty type ?|string, which turns every later check on x into a "cannot prove" warning. :string||number (an empty alternative) warns and simply drops the empty arm. The word unknown is a legal arm and warns about nothing: :unknown|string is ?|string. In a return annotation the same typo makes the method behave as unannotated. When you add an annotation and the diagnostics do not change, check its spelling with confidence: 'all' before looking anywhere else.

Members cannot be annotated in the class body (a :type there would collide with the name: value syntax). TypeChecker.Annotate therefore writes member types as comments, items: false /* :: false|object */, and writes an inferred type it cannot spell natively (any dirty type) as a comment too: /* ?|string */, /* -> ?|number */ for a return.

How types are inferred

The checker runs a sequence of passes over the class: it seeds types from literals and annotations, resolves calls and assignments to a fixed point, executes New abstractly to see which false sentinels are always replaced, applies the guards in each method (narrowing), and only then runs the checks. The subsections below describe the rules a Suneido programmer can observe; the pass order itself is listed in For maintainers.

Members and the four meanings of false

A member's type starts from its literal in the class body and grows with every assignment to it anywhere in the class. The starting type depends on how the literal is spelled, and false in particular means four different things:

After seeding, every literal .m = e or this.m = e anywhere in any method unions the concrete arms of e's type into the member, regardless of control flow. An assignment inside a branch counts the same as one at the top of New. Three things do not count: compound assignment (.count $= "x", .n++), subscript assignment (this[k] = e), and nested assignment (.a.b = e). A member that is never written as a literal and only ever assigned values of unknown type has no type at all and is absent from the result. If, after calls have been resolved, some assignment to a typed member still has an unknown right-hand side, the member becomes dirty: ?|false|object.

Two consequences worth remembering. A private x: false that is assigned true anywhere becomes boolean, and after that if .x isnt false narrows to true, not to a useful value. And the member only ever grows: if a value is assigned from a call whose receiver resolves late, the checker's first guess for that call is unioned in and never removed (the "member ratchet", CB-30).

Calls to builtins

Builtin methods and functions are typed from a signature table. The table has two layers: the executable's own declarations (326 entries in a console build, 668 in the GUI build, which is why checking from a console REPL under-reports Win32 records), and a Suneido layer that TypeChecker.RegisterSignatures replaces wholesale, which the stdlib fills through TypeCheckerSignatures(). An entry in the Suneido layer with the same name and receiver overrides the executable's entry. Overloads are per receiver type: Size is declared once for string and once for object, with possibly different return types.

When the receiver's type is known, the call is matched against the overloads for that receiver: a match gives the declared return type; overloads exist but none accepts the receiver gives the error method "Sort!" on `s` not applicable to receiver of type string; no overload with that name at all is silent (the checker assumes an open world: it could be a user-defined method it cannot see). A union receiver is dispatched arm by arm: if every arm has an overload the returns are unioned; if some arm has none you get not applicable on at least one path of union receiver object|string; no overload for string. If any arm is an instance of a class it cannot resolve, the whole call is silently unknown.

Guessing when the receiver is unknown. If the receiver has no type at all (an unannotated parameter, a value from an unresolved call), the checker scans the table by method name alone:

Overloads named MResultWarning
noneunknownno built-in method "M" on `x` and receiver type unknown
exactly onethat overload's return, and its signature is used for argument and count checksreceiver type unknown; assuming built-in "M" on object
several, all returning the same typethat typereceiver type unknown; "M" has multiple overloads agreeing on return number
several, returning different typesthe dirty union of all of them, e.g. ?|object|stringreceiver type unknown; "M" has ambiguous overloads with differing returns (folded to ?|object|string)

These are warnings rather than errors because the type is a guess: the receiver might be a user class with a method of the same name. The guess is remembered ("taint"): a local assigned directly from a guessed call is itself guessed, and any later error whose evidence is a guessed value is downgraded to a warning with the suffix (type guessed from builtin overloads; receiver unknown) or (type guessed from builtin overloads). Taint travels only through plain assignment, parentheses and ranges; it stops at any operator, so v = p.Size() + 1 is not guessed and a later misuse of v is a full error. Taint is never removed, even if the variable is reassigned. The one exception to the downgrade is $: under the default strictStringConcat: error the guessed $ warning is promoted back to an error, at confidence 0.20. The IDE policy turns that family off.

A few free functions are special. Number(...), String(...), Object(...), Record(...), Display(...) and Type(...) return their obvious type. Date(...) with a constant argument is evaluated at check time: Date("2024-01-01") and Date(year: 2024, month: 13, day: 1) (which normalises) are date; Date(year: 3500) is false; Date() is date; Date(x) with a non-constant argument is date|false. A free builtin declared as returning T|void with a parameter named block (such as Dir) returns void when a block is supplied and T otherwise. A free builtin is never mistaken for a method or vice versa: x.Object() with x unknown warns no built-in method "Object".

Calls to your own methods and classes

.M(...) or this.M(...)
First, if M is a method of this class, the context-sensitive return (next subsection). Otherwise the return that M published earlier in this run, which includes a base class passed as an earlier argument. If that is unknown or void, and the class is named Strings, Numbers, Dates, Objects or Records, the call is dispatched as a builtin on that receiver type. Otherwise the builtin table is scanned by name exactly as for an unknown receiver, but silently: the result is guessed (downstream errors become warnings) and no "assuming built-in" warning is printed. A void own method therefore falls through to the scan and can pick up an unrelated builtin's return.
super.M(...)
The return published by the previous argument in the call, if it is not unknown or void. With no previous argument, unknown.
new X(...)
Always an instance of X, with no lookup at all, so a misspelt class name gives a confident instance of a class that does not exist. Only the argument-count check consults the reference (and only X's own New, not an inherited one).
X(...)
If X is a reference with its own CallClass, that method's return (chosen by the call's arguments when a summary applies, otherwise the seed view, below). If CallClass is inherited from a base in the reference chain, the same but marked guessed. If nothing in the chain defines CallClass, an instance of X. If X is not a reference but a free builtin exists, that builtin. Otherwise silently unknown: a bare call to an unknown name never produces a diagnostic. A reference is preferred over a builtin of the same name.
X.M(...)
Any capitalised identifier is treated as a global class here, even a local variable named Foo. The builtin static table (Date.Begin, Zlib.Members) is consulted first, then the reference's summary, then the reference's seed view of M. Otherwise silently unknown.
x.M(...) where x is an instance of C
If C is the class being checked, its own published return. Otherwise the reference C's instance view of M, looked up on C alone: an inherited method is not found even when the base is also a reference. Unknown methods on instances are always silent.
(expr)(...), fns[0](), x[k](...)
Not typed and not checked.

The seed view and the instance view. When New provably replaces a private : false member (demotion), the class publishes two return types for every method: the instance view, computed after demotion, and the seed view, snapshotted before it. Calls on an instance ((new Widget()).Foo()) use the instance view; calls through the class (Widget.Foo(), bare Widget()) use the seed view, on the reasoning that a static call never ran New. For

Widget = class { x: false  New() { .x = "init" }  Foo() { return .x } }

(new Widget()).Foo() is string and Widget.Foo() is false|string. The seed view exists only when something was demoted, and it is taken before narrowing, so adding a guard inside Foo fixes instance callers but not static callers.

Context-sensitive returns

When a method calls another method of the same class, the callee's return is re-evaluated with the actual arguments, but the only thing the arguments are used for is deciding if p is false and if p isnt false branches. For

get(x = false)
    {
    if x is false
        return "default"
    return x
    }

.get() is string because the argument is the default false and the second path is dead. .get(5) is not number: the first path is dead, but the expression x on the second path keeps the type it has class-wide, so the answer is ?|string. The same holds for a ternary body. Only the literal false decides; if x is true, if x is "", if x is 0, if not x and Boolean?(x) are never decided, and the override is by name, so reassigning x in the body does not change the decision. A caller writing .get(5) + 1 therefore gets operator "+" expects number, got ?|string, an error (at 0.40, because the operand is dirty), even though the runtime returns 5.

Across classes (Foo(...) through CallClass, Foo.M(...), and function references) a simpler summary is used: the first parameter whose return differs when it is false versus not false becomes the discriminator, and the call site picks the arm by whether that argument is provably false or provably not. For Timer(secs = false) returning a number when secs is false and a string otherwise: Timer() is number, Timer(secs: 1) and Timer(0, 1, 2) are string, Timer(secs: s) and Timer(@a) are number|string. Only one parameter per method is summarised: with F(a = false, b = false) guarded on both, F(1) and F(1, 2) both give the union, and only the discriminator's argument matters.

Constructor demotion of : false members

A private member seeded x: false keeps the false arm in every method unless the checker can prove New always replaces it. When it can, every read of .x outside New is retyped with the false arm removed. This is what makes the common idiom

class
    {
    items: false
    New()
        {
        .items = Object()
        }
    Add(x)
        {
        .items.Add(x)      // items is object here, not false|object
        }
    }

check cleanly. All of the following must hold for a member to be demoted:

  • The member is private (lowercase). Public members are never demoted.
  • Its literal contains false (x: false).
  • Abstract execution of New ends with the member holding a type that has no false in it, on every path.
  • No assignment to the member anywhere in the class, in any method, has a right-hand side that could be false. An unknown right-hand side counts as "could be false", so Set(v) { .x = v } with an untyped v blocks demotion for the whole class, as does Reset() { .x = false }, and so does Set(v = false) { if v isnt false { .x = v } } because this test is made before narrowing.
  • The class-wide type minus false is not empty. The demoted type is the class-wide type with false removed, not the type New computed. If the only value ever statically assigned is false the demotion is dropped even when New proved otherwise: 
    class
    {
    x: false
    New() { .init(5) }
    init(v = false) { .x = v }     // v is typed by its default: false
    Get() { return .x + 1 }        // operator "+" expects number, got false
    }

What the abstract execution of New understands: parameters have the type of their default (so New(n = 5) { .x = n } demotes to number and New(n = false) { .x = n } never demotes); a helper is followed only when called as a bare statement .setup() with positional arguments (.x = .setup(), if .setup(), .init(v: 5) do not execute the helper); if, switch and try are joined across their branches, so a switch needs a default that also assigns and a try needs the catch to assign too; loop bodies contribute nothing, even do { .x = 5 } while (false); return throw and throw end the path, but a plain return does not; if .x is <literal> is decided against the literal seed, so if .x is 5 { return }; .x = 5 demotes (the early return is treated as impossible); this[expr] = ... anywhere reachable cancels every demotion in the class; inherited methods are never followed. Recursion is cut rather than joined.

Assert ground truths in New

An Assert(cond) inside New with exactly one positional argument pins a private member's type for the whole class: Assert(Object?(.items)) makes .items an object everywhere, and every assignment to .items in every method, including assignments earlier in New, is then checked against the pin. This works for private members and for private inline-init parameters (New(.items)), at any depth inside New (inside an if, a loop, a block), and the condition is always taken as true regardless of where it sits. The condition grammar is the narrowing grammar: Object?(.x), Type(.x) is "Object", .x is 5, .x isnt false, not, and, or.

What does not pin: Assert(cond, msg: "...") (two arguments), every matcher form (Assert(.x isObject:), Assert(.x is: 5)), public members, and Assert(.x isnt false) when .x is only ever false (there is nothing left to pin). An isnt false assert on a dirty member pins a dirty type. A pin overwrites the member's accumulated type, so a wrong Assert silently retypes every read, and later assignments of other types are reported rather than widening the member. Two asserts in New that cannot be merged, or an assert in another method that contradicts the pin, produce a conflict error positioned at the losing assert. Outside New, an Assert statement narrows the rest of its block (see What narrows) but pins nothing.

Narrowing

Narrowing is how a guard changes the type of a variable or member for the code the guard protects. It is the mechanism that clears most false|X errors, and most of the checker's surprises are cases where a guard that reads clearly to a person does not narrow. This section lists what narrows, what does not, and what undoes a narrowing.

What narrows

A narrowing target is a local variable (through parentheses and an inline assignment, if Object?(x = f())) or a member written as .name or this.name. Nothing else is a target: ob.x, ob[i], Global.x, x.y.z are never narrowed.

Besides if, the guard applies to the condition of while and for loops (inside the body), to the arms of ?:, and to the cases of a bare switch / switch (true) (locals only, one expression per case). Early exit works: after if not Object?(x) return (or throw, break, continue, or a braced block ending in one of those), x is object for the rest of the enclosing block. An if/else whose two arms both exit also counts as an exit.

Two more sources. Assigning a narrower value installs the narrowing: after x = Object() the local is object even if it was false|object before, and the same holds for .m = Object() (the value must be strictly narrower than the variable's pre-narrowing type; see GAP 1). And an Assert written as a statement in a statement list narrows the rest of that list: Assert(Object?(x)), Assert(x isnt: false), Assert(x isObject:), Assert(x isType: "Number"), with or without msg:. This works in any method, not only in New; it must be a statement of a block, not the sole unbraced body of an if.

Narrowing toward a type always produces a clean type: ?|string under Object?(x) becomes object. Narrowing away keeps dirt: under not Object?(x) it stays ?|string. Narrowing a plain false away from false leaves nothing known: Foo(x = false) { if x isnt false return x } publishes a dirty return, so every downstream check is a "cannot prove" warning rather than an error. A contradictory guard does not produce an "unreachable" diagnostic; it silently retypes: x :number; if String?(x) return x publishes number|string.

What does not narrow

  • Truthiness. if x narrows nothing, and is itself an error unless x is boolean. if x is true silences the boolean-context error but narrows toward true, which on false|string is a contradiction retype, not a useful fact.
  • isnt against anything but true/false. x isnt "", x isnt 5, x isnt -1 do nothing. A "" or -1 sentinel cannot be discharged, because there is no "non-empty string" or "non-negative number" type; use a false sentinel instead. x is "" does narrow toward string, which is usually a no-op and occasionally a harmful retype.
  • else if chains with an exit. if P { x = e } else if Q { return } narrows nothing after the chain, and bracing the inner test does not help; hoist the test to the same level as the use (GAP 4).
  • switch on members. switch { case Object?(.x): return .x } still reads false|object; only locals narrow inside a bare switch, a case with two expressions narrows nothing, and nothing established inside a switch flows out of it. A switch (x) on a local narrows each case toward the literal's type.
  • Members through an inline assignment. if false is (x = .Maybe()) refines x; if false is .x = .Maybe() refines nothing.
  • Other people's members. Object?(ob.y), ob.Method?(k), x in (...), x =~ p, x < 0.
  • Blocks and try. Both are transparent: the code inside is walked in the same scope with no join, so a throw-guard inside try narrows the code after the catch that swallows the throw, and a narrowed outer x also retypes a block parameter of the same name.
  • A predicate helper that returns a comparison. noKeys?() { return .lockedKeys is false } exports nothing. The helper must contain literal return true and return false statements, be private, be called as the whole condition (if .noKeys?(), not if .noKeys?() is true), and helpers do not chain.

What kills a refinement

  • Assignment. x = e replaces the fact with e's type when that is narrower, and otherwise deletes it. x += 1, x $= "s", x++ always delete it.
  • Loops. Nothing proven inside a loop body survives past the loop, and a break/continue guard inside a loop narrows nothing after it. A local written anywhere in the loop body (except x = x) loses its guard for the whole body, even when the write preserves the type: after if not Number?(x) return, a loop containing x += 1 warns operator "+=" operand has type ?|number inside the loop.
  • Calls, for members only. A local is never affected by a call. A member fact survives a call unless the call is opaque or the callee (transitively, through this class's own methods) assigns that member. Opaque calls are: any call to a method this class does not define itself, which means every inherited method; super.M(); a call through a computed callee ((.fns[k])()); and any call that passes bare this as an argument (x.Do(this)), which also makes the calling method opaque to its callers. Free calls and calls on other receivers (Global(1), ob.Foo()) never kill anything. Even a killed member is salvaged as "its class-wide type minus false" unless some method somewhere assigns it a value that could be false or is untyped (Clear() { .m = false }, .m = SomeUnresolvedCall()), in which case it goes back to the class-wide type. The salvage turns boolean into true.
  • Leaving an if. A fact that held before an if survives it only if every route through the if keeps some fact about the name. Kills inside a loop body, a switch case, a ternary arm or a block argument do not propagate back out.

The canonical workaround: capture into a local

Because locals survive calls and members do not, the reliable shape is to copy the member into a local once, right after the guard, and use the local:

Save()
    {
    if not Object?(.items)
        return
    items = .items             // items : object, and stays object
    .Refresh()                 // inherited: would have killed the .items fact
    for x in items

    }

The same idea applies to values from builtins: rec = Query1(...), then if rec is false return, and use rec. When the guard cannot be placed at the use, narrow once at a boundary instead: a lazy accessor list() { if .items is false { .items = Object() }; return .items } (the assignment installs the narrowing), or one lookup(num) :object that throws on a miss and is the only place the sentinel is examined.

Every diagnostic

This section has one entry for every message the checker can produce, grouped by what the message is about. Each entry shows the message as it appears (without the confidence prefix; the confidence is given in the severity line), what it means, why the checker concluded it, and what to change. Placeholders in angle brackets stand for the actual names and types. The advice follows a fixed ladder for the false|X family, which accounts for most real errors: remove the optional value at its source (assign the member unconditionally in New, give the parameter a real default); otherwise handle the miss with an exiting branch, preferably by moving up a guard that already exists lower down; otherwise narrow once at a boundary (a lazy accessor, or a single lookup that throws). Reach for Assert last.

Operators

operator "+" expects number, got false|number

Error at 0.90 when the operand is a single type, 0.70 when it is a clean union such as false|number, 0.40 when it is dirty. For $ and $= the diagnostic carries the strictStringConcat flag: its severity is whatever that key is set to (default error; the IDE policy sets off, which removes it) and its confidence is 0.20.

What it means. An operand of + - * / % & | ^ << >>, of their = forms, of ++ -- ~ or unary - is not a number; or an operand of $ / $= is not a string. The type shown is the operand's whole type; the arm that does not fit is the problem.

Why the checker says it. Every arithmetic operator requires numbers on both sides and $ requires strings; each operand is checked on its own against that table, and a union fails if any arm fails. A compound assignment checks both sides, so s += "x" on a string produces two errors, one per operand, and afterwards s is typed number (the operator's result), so a later s++ is silent and a later s $ "y" is a new error.

What to do. When the type is false|number (a = false default, .Find, a : false member) the value really can be false here as far as the checker can tell: move an existing if n is false return above the use, or change the default to 0 and treat that as a behaviour change. For $ with a number or date, use Display(x) or String(x). If you believe the type is simply wrong, run TypeChecker.Annotate to see where it came from; a misspelt annotation on a parameter makes the parameter unannotated and is the most common cause.

operator "$" expects string, got number (type guessed from builtin overloads; receiver unknown)

Warning at 0.35 for arithmetic operators. For $ and $= it is flagged strictStringConcat, so under the default error level it is promoted to an Error at 0.20; the IDE policy removes it.

What it means. The same operand problem, but the operand's type came from a by-name guess: a method was called on an unknown receiver and the checker picked the builtin overloads' return, then that value (or a local assigned from it) reached this operator.

Why the checker says it. A guessed type is evidence, not proof, so the check is downgraded. $ is the exception because the configuration level overrides the severity the checker chose.

What to do. Give the receiver a real type (annotate the parameter it came from). If the guess was right, apply the fix from the previous entry.

operator "$" may fail at runtime: can't convert object to String (operand type false|object)

Error at 0.90 / 0.70 / 0.40 by the operand's shape. Not flagged: it survives strictStringConcat: off.

What it means. One arm of the operand is an object, record, sequence, date, function, block, class or class instance, and $ on such a value throws at run time. The message names only the first such arm; the (operand type ...) suffix shows the whole type when it differs.

Why the checker says it. This is a predicted runtime exception, not a style rule, which is why it is unflagged and full severity even when string concatenation checking is turned off.

What to do. Display(x), String(x) or a Format call. When the type is false|object from a query, guard the false first and display the object.

operator "+" operand has type ?|number cannot prove it is number

Warning at 0.25. Never flagged, so it survives strictStringConcat: off for $ too. Hidden by the IDE policy.

What it means. Every arm the checker knows about fits, but the type is dirty (or completely unknown), so there may be an arm it does not know about.

Why the checker says it. Dirt is an honest "could not determine"; the checker neither accuses nor absolves.

What to do. Usually nothing. If you want the warning gone, remove the dirt at its source: annotate the parameter, or narrow with a predicate (Number?(x)), which produces a clean type, rather than with x isnt false on a plain false, which produces an unknown.

comparison "<" between number and string falls back to Suneido's cross-type ordering (bool < number < string < date < object); relying on this tiebreaker is error-prone and not recommended when operand types are statically known - add runtime type checks on the operands or use Suneido.StrictCompare

Warning by default (strictCrossTypeCompares: warn; error promotes it), flagged, confidence 0.20. Hidden by the IDE policy.

What it means. A < <= > >= comparison whose two operands are single, known types of different kinds: the result depends on Suneido's ordering between kinds rather than on the values.

Why the checker says it. Both operand types are known and differ in rank. It is not reported when either side is a union, an instance, unknown, void, or a function, block or class (those have no rank). n < true does warn.

What to do. Convert one operand so both have the same type, or leave it if the ordering is intended.

Boolean contexts

if condition expects boolean, got number|string

Error at 0.90.

What it means. A condition must be true or false, and the checker found an arm that is neither. The context name is one of if condition, while condition, do-while condition, for condition, ?: condition, operator "And" operand, operator "Or" operand, operator "Not" operand; the last three use the parser's token names, not the Suneido spellings. One diagnostic per context, naming the whole type.

Why the checker says it. Truthiness is not a Suneido concept, so if x on a false|object is an error. This check deliberately ignores dirt: if x with x : ?|number is a full 0.90 error, while a pure unknown condition is assumed boolean and ?|false passes because false is boolean. Each operand of and / or is checked separately, so if a and b with a string and a number gives two operand errors and no if condition error.

What to do. For a sentinel, if x isnt false, which also narrows x. For a value that should be boolean, if x is true silences the check but narrows nothing useful. Do not use if x isnt "" expecting a narrowing; it narrows nothing.

Warning at 0.35.

What it means. The same, but the condition's type is a guess (for example not x.Match("a") with x unknown: the only Match overload returns false|object). A guess-based receiver warning usually accompanies it.

What to do. Type the receiver; then decide as above.

Method calls on a receiver

method "Sort!" on `s` not applicable to receiver of type string

Error at 0.90; Warning at 0.35 with the suffix (receiver type guessed from builtin overloads) when the receiver's type was guessed.

What it means. The signature table has overloads named Sort!, and none of them accepts a string. The backticked part echoes the receiver expression.

Why the checker says it. Dispatch matched the receiver type against every overload of that name and found nothing. It is never reported for this, super or class instances, and never when no overload of that name exists at all (an unknown name is assumed to be a user method). A receiver of type void also lands here (see BUG 3).

What to do. Look at where the receiver's type came from. If it is a genuine misuse, fix the code. If the receiver is void because it came from a reference whose every exit is return throw, see BUG 3.

method "Size" on `x` not applicable on at least one path of union receiver false|object; no overload for false

Error at 0.90; Warning at 0.35 with the guessed suffix.

What it means. The receiver may be one of several types and at least one of them (listed after no overload for) has no such method. This is the classic false sentinel error.

Why the checker says it. A union receiver is dispatched arm by arm; a clean union with a bad arm is an error. Note the asymmetry: if any arm is an instance of a class the checker cannot resolve, the whole call is silently unknown instead.

What to do. Guard the sentinel before the call (if x is false return) and, if the receiver is a member, capture it into a local first because an intervening call to an inherited method would discard the guard. If the guard already exists lower down, move it up. If the value is a member set in New, make the assignment unconditional so the constructor demotion removes the false arm.

method "Size" on `x` not applicable on at least one path of union receiver ?|number|string; no overload for number (receiver union contains ?; unknown arms not checked)

Warning at 0.25.

What it means. The receiver is dirty; among the known arms at least one has the method and at least one does not.

Why the checker says it. Because the receiver is uncertain the checker will not commit to an error. Two neighbouring cases behave differently and can look inconsistent: a dirty receiver whose known arms are all bad (?|number) is silent, and a dirty receiver whose known arms are all good (?|string) resolves to a clean return with no diagnostic at all, so a downstream + 1 on that result is a full error rather than a "cannot prove" warning.

What to do. Type the receiver at its source, or guard with a predicate.

no built-in method "TotallyMadeUp" on `x` and receiver type unknown

Warning at 0.35.

What it means. The receiver has no type and the signature table has no method of that name. It is either a method of a user class the checker cannot see, or a typo.

Why the checker says it. With no receiver type the checker can only scan by name, and the scan found nothing. A free builtin of that name does not count as a method: x.Object() warns here.

What to do. Annotate the receiver with its class (x :Foo) so the call resolves through the reference for Foo; or fix the name.

receiver type unknown; assuming built-in "Sort!" on object

Warning at 0.35.

What it means. The receiver has no type; exactly one builtin overload is named Sort!, so the checker assumes the receiver is that overload's type and uses its signature for the return type and for argument and count checks.

Why the checker says it. It is a guess: a user class could define its own Sort!. The result is marked guessed, so every later diagnostic whose evidence is this value is a warning rather than an error. The same scan is applied silently to .M() when this class has no method M.

What to do. Add a true annotation at the source of the receiver. A capitalised annotation names an exact class.

receiver type unknown; "Size" has multiple overloads agreeing on return number

Warning at 0.35.

What it means. Several overloads share the name and all return the same type, so the return is usable, but no signature is bound: argument and count checks are skipped for this call.

What to do. As above.

receiver type unknown; "Map" has ambiguous overloads with differing returns (folded to ?|object|string)

Warning at 0.35.

What it means. The overloads disagree; the call's type is the dirty union of all their returns.

Why the checker says it. With no receiver type there is no way to choose. Beware of assigning such a value to a member: the concrete arms of this guess are unioned into the member and are never removed, even when the receiver is resolved on a later pass (see CB-30).

What to do. Annotate the receiver. If the value must go into a member, wrap it in the intended constructor (.path = String(x.Replace(...))).

Argument types

argument "x": type string not assignable to declared number

Error at 0.90; Warning at 0.35 with the suffix (type guessed from builtin overloads) when the signature or the argument was guessed.

What it means. The callee's parameter x has a declared type (an annotation on your own method, or a builtin signature) and the argument has an arm that does not fit it.

Why the checker says it. The argument's arms are checked one by one against the declared type. Not checked: an argument whose type is completely unknown (silent, not even a warning); arguments after an @args argument; callees declared with a lone @args; a positional argument whose slot is also given by name (the named one wins at run time and is the one checked). A named argument's diagnostic sits on the argument; a positional argument's diagnostic sits at the start of the enclosing statement (or the enclosing condition or ternary arm).

What to do. Narrow at the call site (guard the sentinel, convert the value). Widen the callee's annotation only if its body actually handles the extra type.

argument `0` to Bar has type number, but "x" is passed on to Scanner which requires string

Error at 0.75; Warning at 0.35 with the guessed suffix.

What it means. Bar has no annotation on x, but it passes x straight to Scanner, whose parameter is declared string; the checker inferred that x must be a string and this call violates it. The backticked part echoes the argument text (truncated to 40 characters). The callee named after passed on to is the root of the chain, not the next hop: with Outer(b) { .Inner(b) } and Inner(a) { Scanner(a) }, the error at .Outer(0) says Scanner and never mentions Inner.

Why the checker says it. A requirement is inferred only in a narrow situation: the parameter is bare, never assigned, has no default, is not a ., @ or _ parameter, is passed directly (not p + 1, not p.Size(), not .F(x: p)), the callee's signature is not a guess, and the callee's parameter is a single known primitive (unions and class instances never produce one; false, true and date do). Any x is false or x isnt false anywhere in the body cancels the requirement for x. Two different demands on one parameter cancel each other silently and permanently. The 0.75 reflects that the requirement is inferred.

What it means. The known arms fit, but the argument is dirty. Silent when the parameter's type was inferred rather than declared (a guess on a guess).

What to do. Usually nothing; otherwise remove the dirt at its source.

Why the checker says it. The whole chain of Bar was available as references and none of it exposes the name. The check is silent when Bar or any of its bases is not a reference, and it never checks the class's own static members (T.x inside T). One known false positive: new X(...) inside a ternary arm, an if/while condition, a for ... in header or a switch case reports no member "*new*" on class X at line 1, column 1 (BUG 1).

What to do. An ordinary bug unless it is the *new* case; for that, use if/else or assign the new to a local first.

Return contracts and annotations

return type string not assignable to declared number

Error at 0.90, positioned at the return.

What it means. The method is annotated :number and this return e has an arm that does not fit.

Why the checker says it. A declared return is a contract checked at every explicit return e after narrowing. A bare return is silent (void fits everything), return throw is ignored, and an implicit trailing expression is not checked at all (Foo() :string { 42 } is silent). If a base class checked in the same call declares Foo() :number, an unannotated Foo in the derived class is held to that contract too. Confidence is 0.90 regardless of the shape of the returned type: false|number|object against number is 0.90 here where the same union under + would be 0.70.

What to do. Narrow before returning, or correct the annotation. Remember the annotation is published to callers verbatim even when the body contradicts it.

return type ?|string contains unknown cannot prove it is assignable to declared string

Warning at 0.35.

What it means. The known arms fit but the returned value is dirty. Common after if x isnt false return x on a plain false parameter, which leaves x unknown.

What to do. Narrow with a predicate instead, or give the parameter an annotation with the intended arms.

return annotation "strin": unknown type name "strin"

Warning at 0.35. Several problems are joined with ; ; the other possible text is empty type alternative.

What it means. An arm of the return annotation is neither a builtin type name nor a capitalised class name. The method is then treated as unannotated (if every arm is bad) or given a dirty type (if only some are). An empty alternative (:string||number) is dropped and the type stays clean.

What to do. Fix the spelling. This warning is hidden by the IDE policy, so when an annotation seems to have no effect, check it with confidence: 'all'.

param "x" annotation "string|strin": unknown type name "strin"

Warning at 0.35.

What it means. The same for a parameter annotation. A single bad arm makes the parameter unannotated; a partly bad union makes it dirty (?|string), which turns every later check on it into a "cannot prove" warning and stops Annotate from rewriting it.

What to do. Fix the spelling.

param "x" default has type false, annotation says string

Error at 0.90, positioned at the parameter.

What it means. The default value does not fit the annotation.

What to do. Include the default's type: x :string|false = false.

Assert ground truths

conflicting Assert ground truths for member .x: number asserted in New, string asserted in New

Error at 0.90, positioned at the losing assert.

What it means. Two Assert statements pin the same private member to types that cannot be merged, or an Assert in another method contradicts the pin made in New. Compatible asserts (equal, narrower, or fitting) merge silently.

What to do. Keep one of them.

member .x is a object ground truth (Assert in New), cannot assign false|object

Error at 0.90, positioned at the assignment.

What it means. New contains Assert(Object?(.x)) (or another single-argument assert about .x), so .x is pinned to object everywhere, and this assignment gives it a value with an arm that does not fit. Dirty or unknown arms of the assigned value are ignored.

Why the checker says it. Every assignment to a pinned member in every method is checked, including assignments in New that come before the assert. So .x = .find(); Assert(.x isnt false) with find returning false|object errors on the line above the assert: adding the assert added an error.

What to do. Assert a type the assignments actually satisfy, or narrow the assigned value first (if v isnt false .x = v is accepted because the check runs after narrowing). If you reached for Assert to clear a false|object error, prefer the other rungs first: an unconditional assignment in New, a lazy accessor, or a guard at the use.

Internal errors

typechecker internal error: Foo: <panic text>

Error at 1.00, with an empty method and position 0 (line 1, column 1).

What it means. The checker itself crashed while checking this argument. The argument's result is empty (for Annotate, the source is returned unchanged); later arguments are still checked, in an environment that the crashed run may have left half-updated.

What to do. Report it with the source that triggered it. Nothing in your code is being diagnosed.

Behaviours that surprise people

These are the checker's behaviours that most often make a developer say "why did it say that?". Each item keeps its number from the study's catalogue (CB-n in MASTER.md) so the two can be cross-referenced. Items that are only visible from inside the Go code are omitted.

Printing, ordering and confidence

CB-1: ? prints first, not last
A dirty type renders as ?|false, ?|number|string, ?|Ca|Cb in every message and in Infer output. Arms are sorted by character code and ? sorts before every letter. Older documentation that shows number|string|? is wrong.
CB-2: any flagged diagnostic scores 0.20, even after promotion to an error
n $ "x" with a number n reports [0.20] operator "$" expects string, got number as an error ranked below every plain 0.35 warning; strictCrossTypeCompares: error yields [0.20] errors. Confidence looks at the flag before the severity. Under the IDE policy >=0.70 the warn and error settings for both flags are indistinguishable (both invisible); only off is observable. Lower the threshold (confidence: 'all') to see them.
CB-3: confidence depends on which check caught the problem, not on the evidence
Foo(c) { x = c is 1 ? "s" : 5    return x + 1 }      // error [0.70]
Baz(c) { x = c is 1 ? "s" : #()  return x.Sort!() }  // error [0.90]
Only the operator checks look at the operand's shape when scoring; return, callsite, arity, member, static and boolean errors are 0.90 by omission. Treat 0.90 on those as "unscored", not "certain".
CB-4: a guess becomes an error by configuration
Bar(p) { v = p.Size() return v $ "x" } produces [0.20] operator "$" expects string, got number (type guessed from builtin overloads; receiver unknown) as an error: the checker emitted a warning, and the default strictStringConcat: error rewrote its severity. strictStringConcat: off removes it; the unflagged "cannot prove" warning for dirty operands survives either way.
CB-5: guessedness is invisible to the confidence score
A "type guessed" warning scores exactly 0.35 like any other warning; only the message suffix tells you it was a guess.
CB-6: the [0.90] prefix is part of the message
Any code that matches message text must strip [d.dd] ; the internal error reads [1.00] typechecker internal error: ....
CB-7: columns count bytes, and unknown positions land at 1:1
A tab is one column and a multi-byte character several. no member "*new*" and other position-less diagnostics appear at line 1, column 1; the internal error has line and column 0.
CB-8: diagnostics within a class are ordered by method name, not by line
For methods in source order Z, A, M the list comes out A, M, Z. The sort is by confidence, then argument order, then method name, then statement order.
CB-9: duplicate diagnostics are normal
.M1((p0.Number?()), (p0.Number?())) reports the same record twice; a guessed call gives both an "assuming built-in" warning and, if the count is wrong, a count warning at the same position. Nothing de-duplicates.
CB-10: a dirty type in a boolean context is a full 0.90 error
if x with x : ?|number gives [0.90] if condition expects boolean, got ?|number, while the same value under + is a 0.25 warning and as a receiver is silent. The boolean check discards dirt; only a pure unknown is assumed boolean, and ?|false passes. Write if x isnt false.
CB-11: positional-argument diagnostics point at the statement, not the argument
return 1 + .F("s", 1) reports at the start of the return; inside a ternary arm or an if condition the anchor is that arm or condition. Only named arguments carry their own position. Argument-count diagnostics use the same anchor.
CB-12: boolean-context labels use the parser's token names
operator "Not" operand expects boolean, operator "And" operand ..., operator "Or" operand ..., whereas operand checks use the Suneido spellings ("+", "$").
CB-15: three checks, three policies for ignorance
An unknown operand under + gets a "cannot prove" warning; a pure-unknown argument is silent while a dirty-union argument warns; a dirty receiver at a member or subscript access is silent.
CB-16: the $-crash message names one arm only
"x" $ f with f : false|object reports can't convert object to String (operand type false|object) and never mentions false: the message stops at the first arm that can crash.
CB-18: the confidence filter grammar is wider than documented, and == is an exact comparison
=, <= and > are accepted; a bare number means >=; ==0.9 works only because the ladder's values are exact.

Seeding, false and returns

CB-19: false means four different things depending on where it is written
flag: false is false; Flag: false is ?|false; Foo(.flag = false) is ?|false even for a lowercase member (and the parameter local too); Foo(.flag :false) is false. Public literals and every dot-parameter default are widened; annotations never are. Pick the spelling whose type you want; the exact false is the one the constructor can demote.
CB-20: true|false is boolean, so a sentinel that is ever assigned true loses its sentinel reading
A private x: false plus .x = true somewhere makes .x a boolean; .x isnt false then narrows to true rather than to a real value. A public x: true is boolean from the start.
CB-21: capitalised dot-parameters write the wrong member name
Foo(.Name = 0) types a member name while .Name = "s" types a member Name, giving two entries (name = number, Name = string) where the run-time member is Name.
CB-22: a dot-parameter without a default never widens its member (GAP 2)
SetModel(.model) records nothing about model; the local is seeded from the member's literal type (typically false), so .model.Foo() in other methods keeps erroring. The longhand SetModel(model) { .model = model } widens the member to ?|false but, because the assigned value is untyped, still blocks constructor demotion. Accept the dirt or annotate the parameter.
CB-23: compound assignment and ++/-- on members never change the member's type
count: 0; Inc() { .count $= "x" } leaves count a number. Locals behave differently: count $= "x" makes the local a string.
CB-24: Foo(x :string = false) is an error
param "x" default has type false, annotation says string at 0.90. Write x :string|false = false.
CB-25: a member assigned only untyped values does not exist
Set(v) { .x = v } with no x: literal gives x no type at all; it is absent from the result and every read is unknown. New(.Width) with no default records nothing either. Absence in the result is not evidence that the member does not exist.
CB-26: a half-bad annotation silently becomes dirt; a fully bad one becomes "unannotated"
x :string|strin gives one 0.35 warning and x : ?|string, so every later check on x degrades to "cannot prove" and Annotate will not rewrite it. x :strin warns and the default value's type silently takes over. Foo() :strin warns and the method behaves as unannotated. Fix the spelling.
CB-27: return annotations are inherited by name across a lineage
A base Foo() :number checked in the same call makes a derived, unannotated Foo() { return "x" } publish number and report return type string not assignable to declared number.
CB-28: a derived class literal overwrites the base's accumulated member type
Base x: 0 plus .x = "s" gives number|string; a derived x: false then resets it to false, losing the base's assignment sites.
CB-29: capitalisation is a type-level switch
Public members are widened, never Assert-pinned and never demoted; a public predicate helper Ready?() exports no postcondition, so renaming ready? to Ready? can turn a clean method into an error; a class named Strings, Numbers, Dates, Objects or Records retypes this.
CB-30: the member ratchet: a member never shrinks past its first-pass guess
New() { x = .Compute()  .path = x.Replace("a", "b") }   // Compute resolves one pass late
Get() { return .path.BeforeLast("/") }
// error [0.90] method "BeforeLast" on `this.path` not applicable on at least one
//   path of union receiver date|object|string
On the first pass x is unknown, so Replace is guessed from all its overloads as ?|date|object|string; the concrete arms are unioned into .path and are never removed once x resolves to string. The error blames the read, and nothing says the arms came from a guess. Wrap the assignment (.path = String(x.Replace(...))) or type x at its source.
CB-31: checking never degrades inference, so a rejected compound assignment retypes the target
s += "x" on a string gives two errors (one per operand, both quoting "+="), and afterwards s is number: s++ two lines later is silent and a later s $ "y" is a new error. x = false; x += 1 publishes number.
CB-32: a trailing expression is an implicit return, and a trailing assignment counts
Trailing() { x = 5 } publishes number; New() { .x = 5 } publishes number (Annotate writes New() :number); Foo() { .Save() } publishes whatever .Save() returns; Tail() { if true { 5 } } is void.
CB-33: return throw is not a return; a method with only that publishes void (BUG 4)
A :number method whose only exit is return throw is silently fine, and x = Catch({...}) against such a reference gives x the type void, which then triggers CB-60.
CB-34: an annotated return is not checked against the implicit trailing expression
Foo() :string { 42 } and Bar() :string { x = 42 } publish string with no diagnostic; only an explicit return 42 is reported.
CB-35: falling off the end is not void
if c return 1 with nothing after publishes number, but if c return; return 1 publishes number|void. "May not return" is visible only when a bare return is written.
CB-36: a declared return is published even when the body contradicts it
Callers of a wrongly annotated method inherit the lie; only the annotated method itself gets the error.

Members, the constructor and the two views

CB-37: Infer's member type and the type used at read sites disagree by design
x: false; New() { .x = 5 }; Get() { return .x } reports members: x: false|number and Get $return: number; Annotate writes x: false /* :: false|number */ and Get() :number. The member listing is the seed view (with false); the demotion is applied to reads in every method except New.
CB-38: calling through the class and through an instance give different return types
Widget.Foo() and bare Widget() resolve to the pre-constructor seed view false|string; (new Widget()).Foo() resolves to string; a :string caller of the static form errors. The reasoning: a static call never ran New.
CB-39: the seed view exists only when something was demoted, and it is a pre-narrowing snapshot
Two references differing only in whether New assigns a sentinel produce differently shaped results. Foo() { if .x is false return "d"; return .x } publishes string as its instance return but false|string as its seed return, so adding a guard inside Foo fixes (new W()).Foo() callers but not W.Foo() callers.
CB-40: the demoted type is the class-wide type minus false, not what New computed
class { x: false
New() { .init(5) }
init(v = false) { .x = v }      // v's type is its default: false
Get() { return .x + 1 } }       // error [0.90] operator "+" expects number, got false
Execution proved number, but removing false from the class-wide type false leaves nothing, so the demotion is dropped. Assign a typed value (Number(v)) or annotate v.
CB-41: a parameter's default is its type during constructor execution
New(n = 5) { .x = n } demotes .x to number although new T(false) is legal; New(n = false) { .x = n } never demotes.
CB-42: helpers are followed only as bare statements, and named arguments are ignored
.setup() as a statement demotes .y, but .x = .setup(), if .setup() ... and .a(.b()) do not execute setup; .init(v: 5) behaves like .init(). Meanwhile the "no method assigns it false" gate looks inside every helper, so a helper can block a demotion but only sometimes cause one.
CB-43: the "no false assignment anywhere" gate is class-wide, pre-narrowing, and treats unknown as "maybe false"
Set(v) { .x = v } (untyped v), Set(v = false) { if v isnt false { .x = v } } or Reset() { .x = false } anywhere blocks demotion of .x for the whole class, even when New calls .Set(5). Assign call results (Object()) rather than parameters in helpers, and keep false assignments out of the class.
CB-44: loops never contribute to demotion; switch needs a default; try needs the catch to assign too
for (...) { .x = 5 } and even do { .x = 5 } while (false) never demote; switch (k) { case 1: .x = 5 } never, but with default: .x = 6 yes; try { .x = 5 } catch { } no, catch { .x = 6 } yes.
CB-45: return throw in New is divergence; plain return is not
if f is 1 { return throw "x" }; .x = 5 still demotes; if f is 1 { return }; .x = 5 does not.
CB-46: if .x is <literal> inside New is decided against the literal seed
if .x is 5 { return }; .x = 5 demotes because the early return is treated as impossible (.x is false at that point). The "init if unset" idiom if .columns is cols return works for the same reason, but a genuine early return compared with a non-boolean value is silently pruned.
CB-47: this[expr] = ... anywhere reachable from New cancels every demotion in the class, silently
Assign through a named member instead, or accept the false arms.
CB-48: inherited methods are never followed by the constructor execution
A subclass calling .Init() defined in the base gets no demotion from it (and, unlike own helpers, the base's assignments do not block one either).
CB-49: the result's members lists only literal class members
.items = Object() in New with no items: literal never shows in the result or in Annotate, though it is typed and used for checking.
CB-50: a local's reported type is the union of every type it took, and may be stale
With get(x = false) { return x is false ? "default" : x }, Foo() { a = .get(); b = .get(5); return a $ b } reports a = string, b = string while Annotate shows the call nodes as ?|string. A variable narrowed in a branch still shows the full union; a name reused for two purposes shows both types.

Calls and dispatch

CB-51: argument binding prunes if p is/isnt false branches and nothing else
.get(5) on get(x = false) { if x is false return "d"; return x } is ?|string, never number; a ternary body gives ?|string for both .get() and .get(5); a caller doing .get(5) + 1 errors while the runtime returns 5.
CB-52: a method's own published return can widen when narrowing runs
The ternary above goes from string to ?|string once narrowing has typed the false-arm read as unknown.
CB-53: the override is by name and ignores reassignment; only the literal false decides
get(x = false) { x = false; if x is false return "d"; return 1 } called as .get(5) gives number (the runtime returns "d"). if x is true, is '', is 0, not x, Boolean?(x) are never decided; isnt false is.
CB-54: only the first discriminating parameter is summarised for cross-class calls
F(a = false, b = false) guarded on both: F(1) and F(1, 2) both give object|string; F(b: 2) gives number.
CB-55: this.M() returns need the base as an argument; signatures do not
Parent { Foo() { return .Bar() } } with Parent only in references gives Foo unknown, yet .Bar(1, 2, 3) reports too many arguments to Bar: 3 given, takes at most 0. Put the lineage in the arguments.
CB-56: instances have no inheritance and no builtins at dispatch
d = new Derived(); d.Val() with Val on Base is silently unknown even with Base and Derived both as references; inst.Size() is unknown; Derived.Val() likewise. Static member reads do walk the bases; method calls do not.
CB-57: an instance arm silences a whole union receiver
x : false|Foo, x.Size() is silent while false|object.Size() is a 0.90 error; Foo|string receivers produce no call diagnostics for any method, yet x.name (a member access, checked per arm) still errors.
CB-58: a false sentinel in a clean union is a hard error on any method call
false|string.Size() gives [0.90] ... no overload for false, even when the false arm came from a builtin's declared return and the code guarded it in a way narrowing does not understand. Test with isnt false first, or capture into a local.
CB-59: dirty union receivers: "some good arm" warns, "all known arms bad" is silent, and the result drops the dirt
?|number|string.Size() warns at 0.25; ?|number.Size() says nothing; ?|string.Size() is a clean number with no diagnostic and no bound signature, so a downstream + 1 is a 0.90 error rather than a "cannot prove" warning. Adding a good arm makes the checker louder.
CB-60: void receivers mismatch (BUG 3), and void is vacuous everywhere else
x = Catch({ 1 }) with a return throw-only reference gives [0.90] method "Size" on `x` not applicable to receiver of type void, while x.name, x + 1, if x and s.Has?(x) on the same x are silent. A void value only arises from a reference whose returns are all return throw.
CB-61: any capitalised identifier is a global class at a call site
Foo.Bar() where Foo is a local variable is dispatched as a static call on a class Foo and never sees the local's type. Consistent with Suneido naming, but a local named with a capital will not be typed.
CB-62: new X() never consults the references
A misspelt class name yields a confident instance of X; only the argument-count check looks X up (and only its own New).
CB-63: bare Foo() prefers a reference class over a builtin of the same name, never diagnoses an unknown name, and marks inherited CallClass results as guessed without saying so
Unknown(...) is silently unknown; Sub() inheriting CallClass from a base is typed but every downstream check is a warning, with no "this was a guess" message; whether Contributions("X") is an instance depends on which references you supplied.
CB-64: a published void return is invisible to this.M() and super.M() dispatch
.Nothing() where Nothing() { } falls through to the builtin by-name scan and may pick up an unrelated builtin's return (GAP 8's Match collision).
CB-65: the this.M() fallback scan is guessed but silent
.Find(5) in a class with no Find is ?|false|number with no "assuming built-in" warning, yet the taint propagates and downstream checks are warnings.
CB-66: union receivers lose their signature when the arms use different overloads
x : string|object, x.Size() resolves to number but no signature is bound, so no argument or count check runs for that call; the same for the "agreeing" and "ambiguous" guesses.
CB-67: guess taint stops at any operator and is never cleared
v = p.Size() + 1; v $ "x" errors at full severity while v = p.Size(); v $ "x" is the guess warning; v = p.Size(); v = 5; return v $ "x" still reports the guessed variant; v = (p.Size()) and v = p.Size()[1..2] are tainted.
CB-68: the Date special case applies only to the bare identifier
Date.Begin() is a static signature, x.Date() a method scan, Date(x) with an unprovable argument is date|false; Date(year: 2024, month: 13, day: 1) is a valid date, Date(year: 3500, ...) is false.
CB-69: a call on an expression callee is invisible
(cond ? f : g)(), fns[0](), x.y[0]() get no type and no diagnostics.
CB-70: signature loading is all-or-nothing and silently keeps the old table
One bad entry in RegisterSignatures throws and the previously published table stays in force; a caller ignoring the exception keeps checking against stale signatures. The table is process-global; the last registration wins.
CB-71: a method whose annotation fails to parse silently loses its signature
Calls to it get no argument or count checks (the parse error is reported separately as a 0.35 warning).
CB-72: block form counts any positional value at the block slot as "the block"
Dir("x", false, false, 5) is typed void.
CB-74: a free builtin never masquerades as a method, and vice versa
x.Object() with x unknown gives no built-in method "Object" on `x` and receiver type unknown; x.Query1('q') warns while Query1('q') resolves.
CB-75: a class named Strings, Numbers, Dates, Objects or Records retypes this; Strings2 or Strings__webgui does not
The name must match exactly.

Narrowing

CB-76: assignment from a narrowed name copies the narrowing only when the narrowed type is a subset of the un-narrowed one (GAP 1)
Foo(item = false) { if not Object?(item) return; menuItem = item; return menuItem }   // menuItem: false
The same code with item :false|object, a dot-parameter .item = false, or item = .Maybe() answers object. A plain = false parameter is exactly false; narrowing it away from false leaves unknown, and unknown is not "narrower" than false, so the assignment keeps the seed. Assign from an expression that is the wanted type, or annotate the parameter.
CB-77: if x isnt false on a plain false value yields unknown, not "non-false"
Foo(x = false) { if x isnt false return x } publishes a dirty type; downstream everything is dirty: no errors, only "cannot prove" warnings. The same for a public .X isnt false on ?|false.
CB-78: contradictory guards retype instead of flagging
x :number; if String?(x) return x publishes number|string; x :false|string; if x is true return x publishes true; String?(x) and Number?(x) narrows to number (the last conjunct wins); Type(x) is "Broski" is a silent no-op. There is no notion of an unreachable branch.
CB-79: kills propagate back only out of if
if not Number?(.x) return; for i in #(1) .x = false; return .x publishes number|string: a refinement destroyed inside a loop body, a switch case, a ternary arm or a block passed to a call survives in the enclosing scope.
CB-80: facts never escape a loop body, and a break/continue guard inside a loop does not narrow after it
for (...) { if false isnt dir = .Maybe() break }; dir.Trim() leaves dir : false|string.
CB-81: a local written anywhere in a loop body loses its guard for the whole body, even when the write preserves the type
if not Number?(x) return; for ... x += 1 warns operator "+=" operand has type ?|number inside the loop, and return x after the loop is the stale pre-loop number; x = x is the only exempt write.
CB-82: try/catch and blocks are transparent
try { if not Number?(x) throw "no" } catch (e) {} return x publishes number: the throw-guard narrows past the catch that swallows it. A guarded outer x also retypes reads of a same-named block parameter.
CB-83: else if with an assignment/exit combination never narrows afterwards (GAP 4)
if P x = e else if Q return leaves nothing narrowed after; bracing the inner test does not help. Hoist the tested if to the same level as the use.
CB-84: members are never narrowed by switch, and a case with two expressions narrows nothing
switch { case Object?(.x): return .x } still reads false|object; case Number?(x), String?(x): narrows nothing although if ... or ... does; nothing merges back after a switch.
CB-85: inline assignment is a narrowing target for locals but not for members
if false is (x = .Maybe()) refines x; if false is .x = .Maybe() refines nothing.
CB-86: isnt narrows only for boolean literals; is narrows for any literal; Type(x) isnt "S" subtracts (GAP 5)
x is "" narrows toward string (usually a no-op, sometimes a harmful retype); x isnt "" and x isnt 5 do nothing; the '' sentinel cannot be discharged because string has no "non-empty" subtype. Use a false sentinel, not '' or -1 (GAP 9).
CB-87: truthiness never narrows
if x is not a narrowing source (and is an error unless x is boolean).
CB-88: "any call on this invalidates a member refinement" is overstated (GAP 7); inherited methods are the real culprit
.other() (which writes only count), .Chain(), Global(1), ob.Foo() keep a narrowed .items; .PassThis(1) where PassThis(x) { x.Do(this) }, super.Foo() via a helper, (.fns[k])(), and .NotDefined() (any inherited method) kill it. Even a killed member survives as "class-wide minus false" unless some method assigns it a false-containing or untyped value (Clear() { .m = false }, .m = SomeUnresolvedCall()). The workaround is to capture into a local: locals are never invalidated by calls.
CB-89: the salvaged type after a call is wider than the guard, and turns boolean into true
if Number?(.x) { .f() ... } where .f may touch .x: .x becomes, say, number|object (the class-wide type minus false).
CB-90: boolean postconditions need a private helper with a literal return true/return false, called directly as the whole condition (GAP 6)
noKeys?() { return .lockedKeys is false } exports nothing; the if/return-literal form does; Uppercase? helpers never export; if .hasKeys?() is true discards it; helpers calling helpers do not chain; a helper that calls a member-writing method before return true loses the fact if any method assigns that member false. Use the if/return-literal form, or hand the value back from the helper.
CB-91: the no-else join treats a sentinel's negative region as empty
p = false; if p is false p = 5; return p publishes number (a caller passing p = "x" is invisible); with p :false|string it publishes number|string.
CB-92: x is false ? A : x on a plain false value is dirty
Set(children = false) { .children = children is false ? Object() : children } passes the call-site check only because the result is ?|object, not because it is clean.
CB-94: the local-typing pass has its own mini early-exit narrowing
Foo(x = false) { if x is false return; return x } publishes ?|void; if x is false return 0; y = x can differ from if not Number?(x) return 0; y = x; the effect reaches every later read including inside loops, where the main narrowing drops its own facts. Only if <local> is <true|false> with a diverging then-branch and no else.
CB-95: Assert narrows only as a statement in a statement list
if c Assert(Number?(x)) (no braces) refines nothing; { Assert(Number?(x)) } refines the rest of that block; Assert(a and b) refines both while Assert(a or b) merges; Assert(x isnt: 5) and Assert(x isSize: 3) do nothing. This works in any method, not only New (GAP 3 as originally written is wrong).
CB-96: Function? admits block; Type(x) is "Function" does not
Use the predicate when blocks are acceptable.
CB-97: narrowing toward drops dirt; narrowing away keeps it
x : ?|string under Object?(x) becomes a clean object; under not Object?(x) it stays ?|string.
CB-99: new X(...) in a ternary arm (or any condition position) reports no member "*new*" on class X at line 1 (BUG 1)
c = p is 1 ? new Ref(1) : new Ref(2) gives two errors at 1:1; for m in Ref.Members(), if Ref.Members(), while ... and switch ... case Global.M(): also hit it when M is not a data member, method or Getter_ of the reference. Use if/else, or assign to a local first.
CB-100: block parameters are not scoped; nested function literals are never walked (BUG 2)
b = 5; f = {|b| b $ "x"} gives operator "$" expects string, got number; f = function() { return 1 + "s" } gives no diagnostic at all. Rename the block parameter.
CB-101: reads inside a loop see the widest loop-carried type; the cap of four iterations is silent
s = ""; while c { s = s.Size() } reports not applicable on at least one path for the number|string receiver inside the loop.
CB-102: join semantics are hybrid
Sequential last-write-wins; branches and loops union; if without else and switch without default keep the entry type; catch sees entry plus end-of-try; there is no "possibly unassigned" arm (a variable first assigned inside one branch simply has that branch's type afterwards); an unknown in one arm makes a dirty union, not unknown.
CB-103: for variables are unknown except over an exact string
for c in "abc" gives string; for k, v in "abc", for x in ob, for i in 0 .. n give unknown.
CB-104: this.member reads are typed only from the member table
A method name read without a call (.Helper) is unknown; local.member is never typed.
CB-105: a contradictory guard splits reads from assignments
f0: false; if false is .f0 return false; return .f0 publishes dirty ?|false, but x = .f0; return x publishes clean false: a read applies the refinement unconditionally, an assignment accepts it only when it is narrower.
CB-106: carrying a guarded parameter out of its guard dirties the return
v0 = 1; if Number?(p0) { v0 = p0 }; return v0 is dirty: at the join the guarded fact degrades to the pre-narrowing one.
CB-108: x.Do(this) makes the calling method opaque for member-write analysis, transitively
Every method that calls it loses all member refinements at that call; x.Do(.items) does not count as an escape.
CB-109: an untyped right-hand side anywhere counts as "assigned false"
One .m = SomeUnresolvedCall() in any method turns every member-touching or opaque call into a hard kill of .m's refinement, and blocks its demotion.

Assert

CB-110: Assert(cond, msg: "...") and every matcher form pin nothing in New; Assert(cond) pins
Assert(.items, isObject:), Assert(x isNumber:), Assert(.x is: 5) are not ground truths although they narrow locally.
CB-111: an Assert anywhere inside New is class-wide, with no reachability or polarity
Inside an if, a loop, a try, or a block literal passed to another method, the condition is applied as true regardless.
CB-112: Assert pins are checked against assignments that precede the Assert in New, and an isnt false assert on a dirty seed pins a dirty type (GAP 3's true half)
.x = .find(); Assert(.x isnt false) with find : false|object pins object and errors on the previous line: member .x is a object ground truth (Assert in New), cannot assign false|object. Adding an Assert can add an error.
CB-113: Assert(.x isnt false) pins nothing when .x is only false, but pins when the union has other arms
Whether it is a ground truth depends on what other methods assign.
CB-114: pinning overwrites the accumulated type; a wrong assert silently retypes every read
After the pin, assignments of other types are reported rather than widening the member.
CB-115: conflict errors sit at the losing assert, and a conflict inside New blames New twice
... number asserted in New, string asserted in New.
CB-116: inline-init public parameters never pin, even via the local name
New(.Width) { Assert(Number?(Width)) } pins nothing (and records no member at all).
CB-117: recursion in the constructor execution is cut, not joined
init(n) { .x = 5; if n is 0 { .init(1) } } demotes; a recursive helper assigning false only in its recursive frame is caught by the class-wide gate, not by execution.
CB-118: "assign it unconditionally in New" silently fails in several situations
When the member is public, when any other method assigns it false or an untyped value, or when the assignment sits in a loop, a switch without default or a try. The rule is: private member, and no method may assign it false or an untyped value.

Requirements, arity and capabilities

CB-119: inferred requirements are much narrower than "infer from uses"
Only a bare, never-assigned, non-defaulted, non-./@/_ parameter passed directly to a non-guessed callee whose matching parameter is a single known primitive produces one; p.Size(), p + 1, p.name, a callee parameter annotated string|number or with an instance type, or .F(x: p) produce nothing. A demand is taken from false, true and date annotations.
CB-120: any x is/isnt false in the body cancels requirements for x everywhere, including uses before the test; the cutoff for other parameters is positional
x is "" and x is 0 do not count.
CB-121: requirement messages name the root callee, not the next hop
Outer(b) { .Inner(b) }, Inner(a) { Scanner(a) }: the error at .Outer(0) reads "b" is passed on to Scanner; Inner is never mentioned. Static callees show as Lib.Wrap, own methods as plain Bar.
CB-122: a requirement conflict is permanent and silent
Two disagreeing demands make the slot unconstrained forever; callers with either type are accepted; no diagnostic says "used as both string and number".
CB-124: argument-count resolution is asymmetric about inheritance
.m(), super.m() and bare Foo(...) walk the base chain; new Foo(...), Foo.m(...) and inst.m(...) use own methods only (new Derived(1, 2) with New(a) on Base is unchecked while Derived(1, 2) errors; d.M(1, 2) on an inherited M is unchecked); new this(...) on a class with a base and no own New is unchecked even when the base's New is loaded, whereas super(...) in the same class is checked.
CB-125: named arguments that match nothing: two checks, two verdicts
The count check ignores them; the argument check warns, except for block and guessed signatures, so x.Sort!(bogus: 1) with unknown x is silent. A trailing { } is the named argument block and never counts positionally: .F() { } on F(x) is missing argument to F: x; .B(1) { } on B(block) is the double-bind warning.
CB-126: in, subscripts and range bounds have no operand checks at all
s in (1, 2), ob[true], ob[#(1)] are silent (only the receiver is checked); is, isnt, =~, !~ are silent by design; cross-type < warns only for two ranked single types (false|number silent, n < true warns, class/function/block unranked).
CB-127: an instance is "callable" without checking for a Call method, and never rangeable or iterable even when the class defines Iter
for y in x with x an instance of T is iteration on `x` not applicable on receiver of type T.
CB-128: member checks skip this/super/global receivers and every dirty receiver, and report rec.n += 1 as a read
So .items.Add(x) is never reported as a member access problem on this; the method call check handles it.

The API and the harness

CB-129: one environment for the whole batch: unrelated arguments contaminate each other (HARNESS 4, broader than described)
// arguments: (A, B)
A = class { x: "s" }
B = class { Bar() { return .x } }   // reported $return: string; B alone has nothing
.Val() and super.Val() resolve to whatever the previous argument published, related or not; member types, returns, guess taint, Assert facts and requirement conflicts all leak; only diagnostics are cleared between arguments. Check one class (with its lineage base-first) per call, as TypeCheckHelper.OrderedSrc does.
CB-130: a base supplied only as a reference gives no inheritance
Derived as the argument with Base only in references: both .Val() and super.Val() are unknown; reversing the arguments (Derived then Base) silently loses inheritance too.
CB-131: a name in both references and arguments: the reference wins for callers
The argument is checked with its own body, but (new Counter()).Value() elsewhere resolves through the reference version.
CB-132: three failure modes, three surfaces
One unparsable argument (including a parse-time constant-fold failure like 1 - "s") kills the whole request as an exception; an unparsable reference vanishes silently; a crash inside the checker becomes a [1.00] diagnostic at line 1 and later arguments continue.
CB-133: unknown config keys are silently ignored; values are strictly validated
A typo such as strictStringConcats yields no error and the default error level.
CB-134: RegisterSignatures returns the layer size, not the table size; Annotations() returns the effective table
Annotations().Size() grows by the number of new names. Passing a single registration object instead of a list now throws expected a list of signatures, got a single signature - wrap it in a list, ...; before that fix it silently registered nothing and wiped the Suneido layer (BUG 6).
CB-135: record and object are the same receiver
Two registrations differing only in that collide (duplicate registration object.Zr); an object entry in the Suneido layer overrides a record entry in the executable's layer.
CB-136: the console signature table is 326 entries; the GUI build has 668 (HARNESS 5)
Typechecking from a console REPL or the bridge under-reports Win32 records. go run -tags gui ./cmd/dumpsigs prints the GUI table; register the difference.
CB-138: a function source is checked as a shim class
Diagnostics for a function argument carry the argument's name as the method; a function calling itself by name resolves only if it is also given as a reference.
CB-139: Annotate writes /* -> unknown */ and /* -> ?|number */ on returns, annotates only identifiers and calls, can land mid-expression, and positions diagnostics against the input
y /* object */.Size() /* number */; .m reads, literals, binary expressions and for variables are never annotated; a respelled declaration keeps the author's arm order while an inferred one is sorted (Pick(s :string|false) :false|string); a multi-line declared annotation is left alone.
CB-143: _Parent { } cannot be parsed by the checker (HARNESS 2)
The override-stack idiom (a record named _Name whose class has base _Name) panics in the parser as invalid reference to _Parent; as a reference it silently vanishes, and a lineage that reaches it is silently truncated.
CB-149: static member checking is silent in three easy-to-misread cases and blind to the class's own statics
The class is not among the references; a base on the chain is unresolved; the class or a base has a generic Getter_; and T.x inside T is never checked.

Annotations

CB-153: unknown is a legal, silent annotation arm; ? is the same type plus a warning; neither can be written back
:unknown|string is ?|string silently; :string|? is the identical type plus unknown type name "?"; Annotate leaves a comment for both.
CB-154: capitalised builtin names are builtins, not classes
:String is string, :Strings is an instance of a class Strings, :Record is object. An instance of a class literally named String (from new String(...)) prints as string but is not the builtin type.
CB-155: instances are opaque names: no inheritance, so :Control rejects a subclass
Non-ASCII initial letters are rejected as annotation arms.
CB-156: a respelled annotation keeps your order and duplicates; an inferred one is sorted
Annotate rewrites : String | False to :string|false, while the inferred comment for the same value prints false|string; record stays record.
CB-158: void is an ordinary union arm and a universal fit
string|void is a legal, printable type (written back as :string|void); a void operand or return is silent at every fit-based check, and only receiver dispatch (CB-60) disagrees.
CB-159: empty alternatives are dropped, not dirtied
:string||number and :string | produce clean types plus a warning; an unknown name produces a dirty type plus a warning.
CB-160: the same annotation typo is a warning in class source but fatal in RegisterSignatures
One bad signature fails the whole registration call.
CB-161: a trailing | or a newline before the type defeats Annotate's respelling
x :a|b| and x:\n\tnumber are left alone by Annotate though the checker still reads a type from them; :Foo? is a valid class annotation.
CB-163: arithmetic result types ignore operands
+ is always number, $ always string; x = "a" + 1 types x as number and reports the operand; dirt is laundered by any operator.

Known bugs and limits

The checker's own bug list (typechecker/BUGSTC.md) was re-examined by the study; the entries below are the corrected versions, with the precise trigger for each and the workaround that actually works.

Bugs

BUG 1: new X(...) in a ternary or a condition reports no member "*new*" on class X at line 1
Trigger. X is a reference and the new X(...) (or a call X.M() where M is not a data member, method or Getter_ of X's chain) sits in a position the parser wraps specially: a ternary condition or arm, an if/while/do-while condition, a for ... in header, or a switch case value. c = p is 1 ? new Ref(1) : new Ref(2) gives two errors at 1:1. The same call as a plain statement or return is fine. Why. The static-member check walks the syntax tree in a way that skips the wrapped call, so it sees the synthetic *new* member as a plain read with no position. Workaround. Use if/else instead of ?:, or assign the new to a local first.
BUG 2: a block parameter is shadowed by an outer variable of the same name, and nested functions are unchecked
Trigger. b = 5; f = {|b| b $ "x"} reports operator "$" expects string, got number: the block body is typed in the enclosing scope and block parameters are not scoped. f = function() { return 1 + "s" } is never looked at. Workaround. Rename the block parameter.
BUG 3: a method call on a void value is an error
Trigger. x = Catch({ ... }) where the referenced Catch's every exit is return throw, so its return is void (BUG 4); then x.Size() gives [0.90] method "Size" on `x` not applicable to receiver of type void. Everything else on the same x (x.name, x + 1, if x, passing it as an argument) is silent, because void fits everything except a method receiver. The bug list names the member-access check; it is actually method dispatch. A void value only arises from a reference; an own method's void return is dispatched as unknown. Workaround. Give the referenced function a normal return on some path, or leave it out of the references so the call is silently unknown.
BUG 4: return throw is not a return; a method with only that publishes void
Trigger. Always() { return throw "x" } is void; a :number method whose only exit is return throw is silently accepted; callers of such a reference get void and then BUG 3. This is deliberate (inside New, return throw is treated as ending the path). Workaround. As for BUG 3.
BUG 5: Infer and Annotate disagreed on a member type
The suspected cause, a member that never shrinks past its first-pass guess, is real (CB-30). The disagreement itself could not be reproduced: both methods run the identical analysis, so the two runs must have been given different inputs (a different lineage, reference set or argument order).
BUG 6: TypeChecker.Annotations() did not report the registered layer
Fixed: Annotations() now returns the effective table in a form RegisterSignatures accepts, and passing a single object instead of a list throws instead of silently clearing the layer.

Gaps in narrowing and inference

GAP 1: assignment from a narrowed variable takes the declared type, not the narrowed one
Trigger. Only when the guard replaces a single-type baseline rather than selecting arms from a union: a plain item = false parameter, a p = 0 parameter, a local typed by a literal. Foo(item = false) { if not Object?(item) return; menuItem = item; return menuItem } gives menuItem : false. With item :false|object, a dot-parameter .item = false, or item = .Maybe(), the assignment takes object. Workaround. Annotate the parameter with the arms it can hold, or assign from an expression that is the wanted type.
GAP 2: a dot-parameter without a default does not widen the member
Trigger. SetModel(.model). Workaround. SetModel(model) { .model = model } widens the member to ?|false; it still blocks constructor demotion because the assigned value is untyped. Annotating the parameter fixes both.
GAP 3: "Assert narrows only in New, only for members" is wrong as stated
A statement-level Assert narrows locals and members for the rest of its block in any method. The two true observations behind it: Assert(cond, msg: ...) and every matcher form pin nothing class-wide in New (only a single-argument Assert(cond) does), and a pin in New is checked against assignments made before it, so .source = .find(); Assert(.source isnt false) with a false|object finder errors on the assignment. Workaround. Use the single-argument form for a ground truth; narrow the assigned value before assigning, or use a lazy accessor instead of an Assert.
GAP 4: an else if chain that mixes an assignment and an exit does not narrow afterwards
Trigger. if P { x = e } else if Q { return }; bracing the inner test does not help. Workaround. Hoist the test to the same level as the use.
GAP 5: only true/false sentinels can be discharged
x isnt "" and x isnt -1 narrow nothing; x is "" narrows toward string (rarely useful); Type(x) isnt "S" does subtract. Workaround. Use false as the sentinel (GAP 9 is the -1 shape of the same problem).
GAP 6: a predicate method does not narrow its caller, except in one shape
Trigger. The helper returns a comparison (noKeys?() { return .lockedKeys is false }), or is public, or is compared (if .h?() is true), or calls another helper. Works when the helper is private, contains literal return true and return false, and is the whole condition. Workaround. Rewrite in that shape, or return the value itself and test it at the call site.
GAP 7: "any call on this invalidates a member refinement" is overstated
Trigger. A call to a method this class does not define itself (every inherited method), super.M(), a computed callee, a call passing bare this, or a call that (transitively through own methods) writes the member. Calls to own methods that do not touch the member, free calls and calls on other receivers keep the refinement. After a kill the member is salvaged as its class-wide type minus false unless some method assigns it a false-containing or untyped value. Workaround. Capture into a local right after the guard; locals are never invalidated by calls.
GAP 8: an untyped parameter fed to Replace/Tr/Find folds to ?|date|object|string
The by-name scan unions every overload's return. Downstream uses get "cannot prove" warnings; on a guessed receiver a boolean-context problem is a warning, not an error. Workaround. Annotate the parameter.
GAP 10 and GAP 11: declared returns and false in arithmetic
A declared return is a hard contract at 0.90 even against false|number|object, where the same union under + is 0.70; false|number under + or Max-style arithmetic is an error at 0.70. Both are the checker working as designed; the lesson is the confidence asymmetry (CB-3).

Harness limits

The console signature table is smaller than the GUI one (HARNESS 5)
A console build knows 326 builtin signatures; the GUI build knows 668. Checking from a console REPL or the bridge reports fewer problems (and more "no built-in method" guesses) on Win32-related records than the IDE does. Workaround. go run -tags gui ./cmd/dumpsigs prints the GUI table as a literal that RegisterSignatures accepts; register the difference.
Desktop and __webgui worlds are checked as one (BUG 7, HARNESS 1, 6, 7)
The checker resolves references purely by the names it is given; it has no notion of which world a record belongs to, and a class named Strings__webgui does not get the Strings treatment. The harness must supply the __webgui variants under their plain names when checking a __webgui chain. Related harness-side limits: references are resolved through Global(), a chain built from the stdlib table alone is blind to non-stdlib bases, and the lineage is read from loaded classes. These are properties of TypeCheckHelper, not of the checker.
_Name override records cannot be parsed (HARNESS 2)
A record that overrides Name by extending _Name makes the checker's parser panic (invalid reference to _Name). As an argument the call throws; as a reference it silently vanishes; a lineage that reaches such a base is silently truncated there. Workaround. None for the record as written; check the classes above and below it separately.
References are not transitive, and instance dispatch never walks bases (HARNESS 3)
The harness collects references one level deep. Even when a base is supplied, (new Derived()).Val() with Val defined on Base is unknown, because instance calls look only at the named class. Workaround. None; such calls are silently untyped.
One batch call cross-contaminates its arguments (HARNESS 4)
See Base classes must be arguments, base-first. The harness checks one lineage per call for this reason.

The pass order

RunPipeline in engine/pipeline.go runs the following over one class, in this order:

  1. WithClass + buildMethodSigs: scope the shared environment to this class and build its own method signatures from annotations; abstract stubs (a body that is exactly one throw) are skipped and methods whose annotations fail to parse are silently dropped.
  2. DateNarrowingPass: evaluate Date(...) calls with constant arguments to date or false.
  3. LocalInference: seed member types from literals, parameter types from annotations and defaults, and stamp every literal, operator, ternary and range node.
  4. NameResolutionPass, MemberAssignmentPass, ReturnUnionPass: the flow-insensitive scope walk, the member backfill from every .m = e, and the first publication of returns.
  5. Fixpoint 1 (up to 64 rounds): CallsiteResolutionPass, SuperCallsiteResolutionPass, NameResolutionPass, MemberAssignmentPass, ReturnUnionPass. Calls, locals, members and returns feed each other until nothing changes. Running the member backfill inside this loop is the cause of the member ratchet.
  6. MemberDirtyPass: a member assigned a still-unknown value becomes dirty. MemberAssignmentPass is deliberately never re-run after this point.
  7. NameResolutionPass, ReturnUnionPass: re-stamp reads with the dirtied members.
  8. AssertMemberPass; if it pinned anything, NameResolutionPass and ReturnUnionPass again.
  9. ConstructorExecPass; if it demoted anything, CaptureSeedReturns (the seed view is born here and only here), CallsiteResolutionPass, ReturnUnionPass.
  10. Fixpoint 2 (up to 64 rounds): FlowNarrowingPass, RefreshTrinaryTypes, CallsiteResolutionPass, SuperCallsiteResolutionPass, clearReturnDiagnostics, ReturnUnionPass. NameResolutionPass is intentionally omitted because it would undo the narrowing; that is also why the locals reported by Infer can be stale.
  11. GuessTaintPass: propagate guessedness through plain assignments.
  12. RequirementPass (up to 64 sweeps): infer parameter requirements from direct pass-through.
  13. AssertAssignmentCheckPass, TypeCheckPass, BooleanConditionCheckPass, CallsiteCheckPass, ArityCheckPass, StaticMemberCheckPass, CapabilityCheckPass: the checks. Order-independent among themselves.
  14. ComputeSummaries: the per-method ReturnSummary used for cross-class discrimination.

Both fixpoints stop when a string signature of Nodes, Params, Returns, Members, PostCtorMembers and PreCtorReturns stops changing; at the 64-round cap they return silently with the last state. Bound signatures and guessed flags are not in the signature. Two further capped loops: the reference registry's phase B re-runs CallsiteResolutionPass + RequirementPass over every reference up to 64 times (it does not re-run ReturnUnionPass, so reference return types depend on reference order while requirements do not), and NameResolutionPass walks each loop body at most 4 times. Only AssertMemberPass, ConstructorExecPass and RequirementPass ever report "changed".

Running a probe and the test helpers

To check what the public API does with a piece of source, build a scratch Go module outside the repository with a replace directive pointing at it and a blank import of builtin so its init() publishes the console signature table:

// go.mod:  module probe
//          require github.com/apmckinlay/gsuneido v0.0.0
//          replace github.com/apmckinlay/gsuneido => C:/Users/apatel/Desktop/typeChecker/gsuneido
import (
    _ "github.com/apmckinlay/gsuneido/builtin"
    "github.com/apmckinlay/gsuneido/typechecker"
)
res, err := typechecker.Process(typechecker.Request{
    Method:     "TypeInfer",           // or "TypeAnnotate"
    Arguments:  []typechecker.SourceEntry{{Name: "T", Src: src}},
    References: refs,                  // base-first
    Config:     map[string]string{"confidence": "all"},
})

Build with GOFLAGS=-mod=mod. Use confidence: "all" or you will not see the 0.20 flagged and 0.35 guessed diagnostics. The console table has 326 entries (no string.Trim, no Win32); add missing signatures with typechecker.RegisterSignatures([]annotations.Registration{...}), or dump the GUI set with go run -tags gui ./cmd/dumpsigs.

Engine unit tests drive RunPipeline directly on one class, with no filtering, no confidence and no flag handling, and the builtin signature table is empty unless the test installs one. The helpers in engine/helpers_test.go: runPasses(src, name) (parse and run in a fresh environment), runPassesWith (seed registry maps first), runPassesWithClasses / runPassesWithClassViews / runPassesWithStatics (seed instance, seed and static views), runPassesWithRefSrcs / runPassesWithRefList (build a real registry from reference sources), mustRun, and withSigs(t, Reg{Kind, Receiver, Class, Name, Sig}) in sigs_test.go, which must run before runPasses and is restored on cleanup. Diagnostic predicates: hasDiag(env, method, sev, substr), errOn, errorCount, hasNotApplicableError, hasOperatorError (matches only "expects number"); countDiagsWith and hasMemberNotFound are hard-coded to a method named Foo. Type predicates: unionContains, isUnionOf (ignores dirt). A minimal experiment:

func TestMyProbe(t *testing.T) {
    withSigs(t, Reg{Receiver: "string", Name: "Size", Sig: "() :number"})
    _, env := runPasses(`class { Foo(s: string) { return s.Size() $ "!" } }`, "T")
